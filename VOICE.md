# VOICE.md

Writing guidance for site copy, docs, product text, and admin messages.

## Voice principles

- Clear, practical, and direct.
- Builder-minded: concrete work, decisions, progress, tradeoffs.
- Confident without hype.
- Personal without being overly polished or corporate.
- Short enough to scan, specific enough to be useful.

## Public-site copy

- Prefer plain language over buzzwords.
- Keep Zack's first-person voice grounded in shipped work and current learning.
- Good texture: `real`, `shipping`, `systems`, `workflow`, `build`, `progress`, `validated`, `practical`.
- Avoid vague claims like `revolutionary`, `world-class`, `next-generation`, or `AI-powered` unless the context proves it.

## The Build Log

- Use an honest build-in-public tone.
- It is fine to mention mistakes, decisions, and uncertainty.
- Favor tangible details over motivational filler.
- CTAs should feel lightweight: read, subscribe, see builds, follow progress.

## Newsletter consent and form copy

- Be explicit and honest about what subscribing does: the user gets the Build Log
  by **email**, plus **optional SMS** updates only if they add a phone number.
- Standard consent line: "I agree to get the Build Log by email — plus optional SMS
  updates if I add a phone number — per the Privacy Policy & Terms."
- Mark the phone field as optional in its placeholder/label; never imply SMS is
  required. Do not collect age or other fields the backend does not need surfaced.

## Briefly/admin product text

- Keep UI messages operational:
  - Say what happened.
  - Say what to do next when action is needed.
  - Include IDs, versions, or conflict details when useful.
- Error messages should be calm and repair-oriented.
- Avoid cute status text in admin or infrastructure workflows.

## Documentation voice

- Write docs as working contracts.
- Prefer short bullets and current-state facts.
- Mark aspirations as plans, not facts.
- Include deployment status clearly when deployment is relevant.
